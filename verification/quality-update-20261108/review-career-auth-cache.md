## Original finding 1. [P1, resolved] Gate remounted consumers before exposing the old cached career

Primary location: `C:/Users/User/Documents/ChatGPT/DAVI ANDRIAN THOMAZINI/quality-update-20261108/src/hooks/useCareer.ts:324` (the new `waitForCareerLocalWrites` call).

The wait protects only `queryFn`; a new hook instance can immediately consume an already cached `CareerQueryData` whose status is `ready`. `careerStatus` at lines 634–639 deliberately remains ready while that query fetches, and a fresh cache can skip `queryFn` entirely for the 30-second `staleTime`. The authenticated update does not publish `prepared` into that cache when accepted (lines 1138–1147); it publishes only after the local snapshot, queue and barrier operations complete (lines 878–893). Thus the new route can show and mutate the old career while the accepted save is still writing.

This has a concrete owning caller: `src/pages/match.tsx:536–538` calls `update(next)` and immediately navigates to `/club`. `ClubHub` reads `useCareer` at `src/pages/club.tsx:36` and provides actions based on that returned career. The new hook has its own mutation gate (`useCareer.ts:218`, and the outgoing hook replaces its gate on cleanup at lines 270–275), so it can accept a second update derived from the old cached state. Both writes use the same owner/epoch/generation and may serialize correctly through the career lock, but the second payload was already prepared from the stale state; nothing checks its source revision before replacing the snapshot and outbox. If the first remote upload fails, the second payload can replace the only queued continuation containing the match result. Same-round changes can also be overwritten without a progress-score difference.

The intended guarantee that remount hydration waits for accepted local writes is therefore incomplete. A slow/deferred IndexedDB write is enough; no account switch, invalid payload or malicious input is needed. Move the acceptance/durability gate into shared owner/epoch state used by every hook instance, and prevent a cached ready snapshot from accepting another mutation until the retained local write settles and the resulting state is observed. Preserve the existing separation between local durability and a slow cloud response.

Required regression coverage: defer a local persistence boundary, accept a result in one real hook instance, unmount it, mount a second instance with the same React Query client and old cached ready data, and attempt a change from the second screen before releasing the deferred write. Verify that it cannot overwrite the accepted result or its outbox, including a failed cloud upload. The current lifecycle harness tests one instance and explicitly invokes its query function for hydration cases, so it does not exercise this cache/remount path.

## Original finding 2. [P1, resolved] Make the alternate OAuth path usable with the actual broker SDK

Primary location: `C:/Users/User/Documents/ChatGPT/DAVI ANDRIAN THOMAZINI/quality-update-20261108/src/integrations/supabase/oauth-recovery.ts:60` (the broker result handling; related classifier at lines 20–33).

The new recovery helper depends on the broker returning or throwing a structured transport/credit error. Its actual caller is `src/pages/auth.tsx:302–304`, which uses `src/integrations/lovable/index.ts:15–34` and the installed `@lovable.dev/cloud-auth-js` **1.2.1**. In `node_modules/@lovable.dev/cloud-auth-js/dist/index.js:94–99`, the normal browser path assigns `window.location.href` to `/~oauth/initiate` and immediately returns `{ error: null, redirected: true }`. The helper consequently returns at line 62 before the broker responds. A credit/5xx outage occurs after the application has already navigated away, so the configured direct fallback cannot run.

The iframe/popup path also does not supply the synthetic errors used by the new tests: the SDK's `processOAuthResponse` at dependency lines 46–50 converts broker failures to plain `new Error(error_description)` and discards their `error` code/status. Such an error is neither a `TypeError` nor an object with the classifier's `status`/`code`, so a credit-exhaustion response still cannot trigger fallback. The helper's `{ status: 402 }` / `{ code: "insufficient_credits" }` unit cases do not represent the owning adapter.

This leaves the requested independent login route unusable during the principal broker outages despite an explicit same-project provider configuration. The same Supabase client and direct-provider allowlist are correctly preserved; the missing piece is an actual reachable alternative. Provide an explicit direct sign-in action for providers with separately configured credentials in that same project, or implement an adapter/callback protocol that safely exposes verified broker outages without leaving recovery dependent on metadata the SDK discards. Do not classify arbitrary human-readable account/cancellation errors as outages. Update the documentation so it distinguishes any supported automatic import/network recovery from broker redirects for which automatic credit recovery cannot be observed.

Required regression coverage should exercise the real adapter contract: normal-browser `redirected: true`, popup errors represented as plain `Error`, and the explicit alternate action if that is the selected solution. A live external OAuth consent or real user email is not necessary for these local contract checks.
