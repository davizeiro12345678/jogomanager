# Plano mestre e acompanhamento — JogoManager

**Integração:** PR #125 de `davizeiro12345678/jogomanager`, branch `codex/career-tutorial-css-20261107`. **Data:** 7 de novembro de 2026. Este plano reúne o escopo aprovado e o trabalho existente no PR com o lote adicional das nove frentes. A auditoria inicial usou 15 especialistas; a continuação implementou nove lotes independentes. Código em PR, teste local, CI e produção são estados distintos.

O objetivo é melhorar a carreira, tutorial e estádio 3D, reduzir os monólitos sem alterar determinismo, tornar as integrações seguras e produzir evidências verificáveis. Saves e replays devem continuar compatíveis; o cliente não pode autorizar moeda, compra ou recompensa.

## Sequência de execução

1. Integrar as frentes sem sobrescrever mudanças concorrentes do branch, revisar o diff e executar os gates gerais. Não reescrever histórico Lovable ou forçar push.
2. Repetir Lighthouse mobile no protocolo real e corrigir causas de TBT/LCP, sem afrouxar budgets, eliminar cenários, adiar medições artificiosamente ou transformar assertions em warnings.
3. Capturar a interface compilada de carreira/tutorial e registrar viewport, revisão, estados, recursos faltantes e limitação de GPU. Guardar imagens antes/depois apenas quando ambas as revisões tiverem o mesmo protocolo.
4. Publicar o lote no PR #125 e verificar os checks do SHA exato. Falha, ausência, cancelamento ou skip de um check obrigatório bloqueia release.
5. Concluir os itens operacionais dependentes de provedor, backend e integração escolhida. Migrations/retention, FCM, DNS/email, disavow e teste ativo de invasão não são inferidos por um push de código.

## Salvaguardas

Esta continuação não executou payloads contra produção, brute force, stress externo, deleção de dados, VACUUM FULL, DROP INDEX, mudanças DNS/WAF, pagamentos ou envios reais de email. O teste SQL usou um PostgreSQL local descartável, roles sintéticas e rollback dos fixtures. O contato em security.txt é o endereço já usado pelo projeto; nenhum canal novo foi inventado. A observabilidade é privada e não devolve dados pessoais.

A conclusão deve separar o que está no PR do que foi aplicado. É proibido declarar “tudo concluído” enquanto faltarem gates, evidência de hardware ou ativações operacionais. O release só é identificado pela revisão aprovada e pelo commit efetivamente entregue em `/api/health` após publicação.
